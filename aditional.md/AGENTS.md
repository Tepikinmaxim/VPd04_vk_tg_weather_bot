# Общие правила для всех проектов

Эти правила применяются ко всем проектам и учебным заданиям пользователя, независимо от их расположения и каталога запуска opencode.

## Планирование этапов и подтверждение

- Любой запрос сначала оцени: если ответ можно дать из известного контекста
  без поиска, инструментов и изменений, разрешается ответить сразу.
- Если нужны поиск в интернете, поиск или чтение файлов, запуск команд,
  тестов, установка зависимостей, изменение файлов или другие действия,
  сначала составь план по этапам.
- Этап — это законченный шаг с проверяемым результатом: исследование, анализ,
  реализация, проверка или запуск. Дробить этап на микродействия не нужно.
- Для простой задачи план может состоять из одного-трёх пунктов; для сложной —
  подробнее, с указанием файлов, источников, команд и способа проверки.
- Показывай план в чате и явно спрашивай подтверждение. Подтверждением
  считается только явный ответ пользователя; молчание и отсутствие возражений
  не считаются.
- После подтверждения выполняй весь согласованный этап без повторных
  согласований на каждое чтение файла или отдельную команду.
- Если меняется существенный шаг, объём работ, затрагиваемые файлы, подход или
  риск, остановись, обнови план и снова получи подтверждение.
- В Build-режиме перед началом этапа кратко сообщай, что начинаешь делать и
  зачем; после завершения этапа сообщай результат, изменённые файлы и
  выполненные проверки.
- Не выполняй скрытых действий: источники, файлы и команды должны
  соответствовать согласованному этапу.
- Правило действует независимо от статуса Plan или Build и имеет приоритет над
  привычкой сразу приступать к работе.
- Для проектной задачи после согласования сначала зафиксируй план в `plan.md`,
  затем выполняй этапы.

## Документация на русском

- Без отдельного напоминания создавай или актуализируй `README.md` и `plan.md` на русском языке в каждом проекте, с которым ведётся работа, включая диагностику, консультации и задачи без изменения кода.
- `plan.md` создавай или обновляй до начала работы и сохраняй на диск. План, озвученный только в чате, не считается выполнением этого требования.
- В `README.md` по мере уместности указывай назначение и возможности проекта, требования и зависимости, установку, команды запуска и проверки, структуру файлов, формат входных/выходных данных и известные ограничения.
- В `plan.md` фиксируй цель, основные этапы реализации и проверки. После выполнения задачи отражай фактически сделанное и результаты верификации, а не оставляй устаревший план как обещание будущей работы.
- Документация должна соответствовать текущей реализации. Не выдумывай возможности, команды и результаты проверок.
- Если файл уже содержит полезную информацию, сохраняй её и вноси минимально необходимые изменения. Не перезаписывай пользовательский текст без причины. Имена кода, команд, библиотек и API оставляй в оригинальном написании.

## Точки входа и CLI

- Если проект предоставляет CLI, создавай явную точку входа: файл `cli.py`/`main.py` в корне или пакет `cli/` с `__main__.py`. Не прячь CLI только в конце библиотечного модуля: пользователь должен видеть его в структуре проекта.
- Наличие `if __name__ == "__main__"` в библиотечном модуле не заменяет отдельную точку входа CLI. Модуль может оставаться запускаемым для совместимости.
- Указывай точку входа CLI в `README.md` и `plan.md`; команды запуска в README приводи через неё (`python cli.py`, `python -m cli` или аналог).
- CLI по умолчанию должен выводить человекочитаемый структурированный текст: разделы, русские подписи параметров и значения с единицами измерения. JSON и другие машиночитаемые форматы — только по явному флагу.
- Интерактивный запуск без аргументов должен подсказывать, что делать, а не завершаться ошибкой там, где данные можно запросить у пользователя.
- Перед завершением проверяй пользовательский сценарий: запуск без аргументов, подсказки, базовый и расширенный вывод, ошибки.
- Если формат вывода или UX неоднозначны, сначала согласуй их с пользователем.

## Запуск после согласованных правок

- Перед запуском, проверкой или демонстрацией проекта сверяй действие с согласованным списком правок. Если правки ещё не внесены, сначала сообщи об этом и не запускай старую версию как выполнение задачи.
- Запуск текущей версии допустим как диагностика, только если явно обозначить, что согласованные изменения не реализованы, перечислить их и получить согласие пользователя.
- Не подменяй готовность функциональности фактом запуска: отделяй «код запущен» от «запрошенные изменения внесены и проверены».

## Ошибки и обратная связь

- При ошибке, неожиданном поведении или неудачном запуске сначала объясняй пользователю вероятную причину и план исправления, затем исправляй.
- После исправления кратко сообщай, что изменено и как это проверено.
- Если причина внешняя (сеть, API, окружение), отделяй её от ошибок кода и предлагай проверку или обходной путь.
- При фиксации ошибки и понимании её причины всегда анализируй, что привело к неверному поведению и почему это не было обнаружено раньше.
- Сразу предлагай пользователю конкретное правило для `AGENTS.md`, которое поможет исключить повторение, даже если ошибка не кажется серьёзной.
- Записывай это правило в `AGENTS.md` только после явного подтверждения.
- Если конкретное общее правило неуместно, например из-за внешней причины, объясни это и зафиксируй вывод в `plan.md` проекта.

## Согласование общих правил

- Новые общие правила для будущих проектов сначала предлагай пользователю в чате.
- Записывай их в `AGENTS.md` только после явного подтверждения.
- Существующие правила не удаляй и не переписывай без необходимости; добавляй минимальные изменения.

## Очередь согласованных правок

- В `plan.md` веди раздел «Очередь правок» со статусами: согласовано,
  в работе, проверено, отложено.
- При новом запросе сначала проверяй очередь: ранее согласованные, но
  невыполненные пункты не должны теряться.
- Для каждой правки добавляй тест, воспроизводящий требование; зелёный набор
  тестов без такого теста не считается проверкой.
- Перед итоговым отчётом сверяй очередь и явно перечисляй, что осталось
  невыполненным или отложенным.

## API-ключи и файлы окружения

- Если проект использует внешние API или другие секреты, всегда создавай `.env`, `.env.example` и добавляй `.env` в `.gitignore`.
- Имена переменных и их назначение определяются API конкретного проекта, его кодом и README. Не переноси переменные и заглушки из других проектов.
- В `.env.example` указывай только переменные, которые действительно читает код проекта. Для каждой переменной после `=` указывай понятную нейтральную заглушку, объясняющую, что вставить; не оставляй значение пустым.
- В `.env` над каждой переменной добавляй краткий комментарий на русском: что это за значение и где его взять. После `=` оставляй пустое место для реального секрета; не вставляй заглушку.
- Сохраняй существующие соглашения проекта об именах переменных.
- Не копируй и не придумывай секреты. Никогда не логируй и не коммить реальные ключи.
- Загружай переменные через `python-dotenv` или аналог, проверяй обязательные значения при запуске и документируй их в README.
- Любой токен или ключ читается только из `.env` через `python-dotenv`; не передавай его аргументом CLI, не хардкодь и не выводи в логи.
- При добавлении нового API добавь переменную в `.env.example` с понятной заглушкой после `=` и в `.env` — строку `ИМЯ_ПЕРЕМЕННОЙ=` с комментарием над ней, чтобы пользователю осталось только вставить значение.
- В `.env` не оставляй заглушки вроде `your_token_here` для новых токенов: после `=` должно быть пусто, а назначение объясняй комментарием.
- При запуске проверяй обязательные переменные; если значение пустое, выведи в терминал сообщение с именем переменной и просьбой заполнить `.env`, не раскрывая секрет.
- В `.env.example` храни только имена переменных с нейтральными заглушками без реальных значений; `.env` остаётся в `.gitignore`.

## Документация внешних API

- Для настройки взаимодействия с VK, чат-ботов и Long Poll API используй официальную документацию: <https://dev.vk.com/ru/api/bots/development/app-interaction>. Для Bots Long Poll API — <https://vk.com/dev/bots_longpoll>. Перед изменением сценария, событий или переменных окружения сверяйся с актуальной версией страницы.
- Если официальная страница недоступна без JavaScript, зафиксируй это в `plan.md` и проверь параметры по официальному справочнику VK API и документации используемой библиотеки; не выдумывай названия методов и событий.

## VK-боты: настройки сообщества

- Перед диагностикой молчания VK-бота проверяй настройки сообщества, а не только код, токен и Long Poll.
- В `Управление → Сообщения → Настройки для бота` должны быть включены `Возможности ботов` и `Добавить кнопку «Начать»`; при необходимости — `Разрешать добавлять сообщество в чаты`.
- Если `Возможности ботов` выключены, диалог с сообществом может не открываться, кнопка «Начать» не появляется, а события не поступают. Это не ошибка кода и не повод сразу менять обработчики.
- После включения проверь, что диалог открывается с личного аккаунта. Сообщения с `out=1` и `from_id=-<id сообщества>` — исходящие от имени сообщества; бот не получает их как входящие. Для проверки отправь `/start` с личного аккаунта.
- Только после этого проверяй Long Poll (`is_enabled`, `message_new`), токен, `--check` и handlers.

## Среда разработки пользователя

- Учитывай, что основная машина пользователя — MacBook Pro 13″ Early 2015, Intel, macOS Monterey 12.7.6, 8 ГБ ОЗУ.
- Пакеты устанавливаются через MacPorts. Homebrew не установлен: используй MacPorts (`port`) либо уже имеющиеся проектные средства; не предполагай наличие `brew` и не устанавливай его без прямой просьбы.
- Проверяй совместимость рекомендуемых инструментов и версий с Intel и macOS Monterey. Предпочитай решения с умеренным потреблением памяти; заранее обозначай возможную несовместимость или тяжёлые требования.
- Не устанавливай лишние системные пакеты и зависимости. Следуй ограничениям и разрешениям пользователя и используй существующий проектный стек.

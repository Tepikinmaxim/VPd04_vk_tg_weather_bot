# План реализации VK Weather Bot

Дата: 26.10.2026.

## Цель

Перевести проект на production-ready VK Community Bot на high-level VKBottle
через Long Poll API по ТЗ из `promt.md`: FSM, кнопочное меню, геолокация,
прогноз, расширенная погода, отдельный сервисный слой и emoji-форматтер.

## Принятые решения

- Новый пакет `weather_vk_bot/` становится основной реализацией.
- Текущий `vk_bot.py` на low-level `API` + `BotPolling` остаётся как legacy;
  его код и 22 теста не удаляем.
- Основная точка входа — корневой `main.py`; логика запуска находится в
  `weather_vk_bot/main.py`.
- Для геолокации используется нативная кнопка VKBottle `Location`; резервный
  вариант — ручной ввод координат.
- `VK_GROUP_ID` удаляется из `.env` и `.env.example`; high-level `Bot`
  определяет сообщество по токену. Legacy-бот при отсутствии переменной также
  определяет группу автоматически.
- `StateDispenser` в VKBottle 4.11 отсутствует как импорт; используем
  `BuiltinStateDispenser` и `BaseStateGroup`.
- `message.geo` доступен через `MessagesMessage.geo`; координаты берутся из
  `geo.coordinates.latitude` и `geo.coordinates.longitude`.
- `Callback` не добавляем без отдельного inline-сценария: текстовые кнопки и
  `Location` покрывают требования ТЗ.
- FSM и `CtxStorage` хранятся в памяти процесса; после перезапуска состояние
  сбрасывается.
- Реальные токены читаются только из `.env`; в логи и сообщения не попадают.

## Этапы

### 1. Каркас и точка входа

- Создать пакет `weather_vk_bot/`:
  - `__init__.py`;
  - `bot.py`;
  - `main.py`;
  - `handlers/` с `menu.py`, `weather.py`, `forecast.py`, `geo.py`, `help.py`;
  - `services/` с `weather_service.py`, `formatter.py`, `state_manager.py`;
  - `keyboards/` с `main_keyboard.py`.
- Корневой `main.py` сделать тонкой обёрткой над `weather_vk_bot.main`.
- Обеспечить запуск `python main.py` и проверку `python main.py --check`.
- Перед реализацией обновить `plan.md` и зафиксировать ссылку на этот план.

### 2. Конфигурация и безопасность

- Загружать `.env` через `python-dotenv`.
- Проверять обязательные переменные при запуске:
  - `VK_BOT_TOKEN`;
  - `OPENWEATHER_API_KEY`.
- Удалить `VK_GROUP_ID` из `.env` и `.env.example`.
- Не выводить значения токенов в логи, ошибки и сообщения пользователю.
- Перенести исправление SSL из legacy-бота: кастомный `AiohttpClient` с
  `certifi` и `ssl.create_default_context`.
- Настроить `logging` без записи полного текста пользовательских сообщений.

### 3. Класс `VKWeatherBot`

- В `weather_vk_bot/bot.py` собрать:
  - high-level `Bot`;
  - кастомный `API` с SSL-клиентом;
  - `BuiltinStateDispenser`;
  - `CtxStorage`;
  - `WeatherService`;
  - `StateManager`.
- Зарегистрировать handlers и логирующий middleware.
- Добавить корректное завершение и закрытие HTTP-клиента.
- Реализовать `--check`: проверить токен и доступ к сообществу без запуска
  Long Poll.

### 4. Сервисный слой

- `weather_service.py` — async-обёртка над `OpenWeatherAPI`.
- Все синхронные запросы выполнять через `asyncio.to_thread`.
- Методы:
  - текущая погода по городу;
  - прогноз по городу;
  - текущая погода по координатам;
  - поддержка `extended=True`.
- Создавать отдельный `OpenWeatherAPI` на запрос, чтобы не использовать общий
  `requests.Session` из разных потоков.
- Пробрасывать `CityNotFoundError`, `APIConnectionError` и
  `OpenWeatherAPIError` в handlers без раскрытия API-ключа.

### 5. FSM и контекст

- В `state_manager.py` определить `BotState` на базе `BaseStateGroup`:
  - `MAIN_MENU`;
  - `WAITING_CITY` со значением `awaiting_city_weather`;
  - `WAITING_FORECAST_CITY` со значением `awaiting_city_forecast`;
  - `WAITING_GEO`;
  - `WAITING_EXTENDED` со значением `awaiting_extended_city`;
  - `WAITING_CHANGE_CITY` со значением `awaiting_new_city`;
  - `WAITING_COMPARE_CITY_1` и `WAITING_COMPARE_CITY_2` для сравнения.
- Обернуть `BuiltinStateDispenser` методами установки состояния, получения
  payload и сброса.
- Использовать `CtxStorage` для последнего города и режима, чтобы архитектура
  была готова к избранным городам и персональным настройкам.
- Не хранить токены и секреты в состоянии или контексте.

### 6. Клавиатуры

- Главное меню (7 кнопок):
  - `🌤 Погода сейчас` — `PRIMARY`;
  - `📅 Прогноз 5 дней` — `POSITIVE`;
  - `📊 Сравнить погоду` — `PRIMARY`;
  - `🌫 Расширенный режим` — `SECONDARY`;
  - `📍 Геолокация` — `SECONDARY`;
  - `🏙 Сменить город` — `SECONDARY`;
  - `ℹ️ Помощь` — `SECONDARY`.
- Отдельных кнопок навигации нет: после успешного результата к сообщению
  прикрепляется главное меню; для прерывания ввода используется `/cancel`.
- Для всех основных клавиатур:
  - `Keyboard(one_time=False, inline=False)`;
  - emoji и текстовые разделители в сообщениях.
- Отдельная клавиатура геолокации:
  - нативная `Location()`;
  - кнопка ручного ввода координат.

### 7. Handlers и пользовательские сценарии

- `menu.py`:
  - `/start` и главное меню;
  - погода, прогноз и расширенный режим используют сохранённый `last_city`;
  - «Сменить город» → `WAITING_CHANGE_CITY`, сохранение и возврат в меню;
  - `/cancel` — возврат в главное меню из ожидания ввода.
- `weather.py`:
  - кнопка «Погода сейчас» без сохранённого города → `WAITING_CITY`;
  - ввод города → `get_weather_by_city`;
  - ответ, сохранение канонического города и возврат в главное меню.
- `forecast.py`:
  - кнопка «Прогноз 5 дней» без сохранённого города → `WAITING_FORECAST_CITY`;
  - ввод города → `get_forecast_by_city`.
- `comparison.py`:
  - текущий город как первый, запрос второго;
  - без текущего города — запрос обоих;
  - параллельный `get_current` для двух городов и `format_comparison`.
- `geo.py`:
  - кнопка «Геолокация» → `WAITING_GEO`;
  - проверка `message.geo`;
  - fallback `_parse_coordinates` для форматов `55.7558,37.6173` и
    `55.7558 37.6173`;
  - проверка диапазонов широты и долготы;
  - запрос `get_weather_by_coordinates`;
  - сохранение определённого города.
- `help.py`:
  - инструкция по кнопкам;
  - формат координат;
  - пояснение, что геолокация зависит от разрешения пользователя.
- Обработать:
  - пустой ввод;
  - город не найден;
  - недоступность OpenWeather;
  - неверные координаты;
  - отсутствие геолокации;
  - неизвестную команду;
  - ошибки VK API без раскрытия токена.
- Длинные сообщения делить на части; `random_id` задавать явно.
- После успешного ответа сбрасывать состояние в `MAIN_MENU` и прикреплять
  главное меню к сообщению с результатом; отдельное сообщение меню не отправлять.

### 8. Форматтер

- `formatter.py` отвечает только за оформление, без запросов к API.
- Базовая погода:
  - город;
  - температура;
  - ощущаемая температура;
  - влажность;
  - ветер;
  - облачность.
- Расширенный режим:
  - давление;
  - видимость;
  - рассвет и закат;
  - AQI;
  - загрязнители;
  - `human_summary`.
- Прогноз:
  - пять дней;
  - по одному блоку на 12:00 MSK;
  - явное указание времени среза.
- Сравнение:
  - два блока текущей погоды;
  - разница температур с направлением;
  - отсутствующие температуры не выдумывать.
- Единицы измерения и emoji по ТЗ; отсутствующие значения показывать как `—`.
- Для выбора дневного среза использовать публичный helper, чтобы не
  дублировать приватную логику `OpenWeatherAPI.py`.

## Ограничения

- FSM и `CtxStorage` не сохраняются между перезапусками.
- Нативная геолокация зависит от разрешения пользователя и возможностей
  клиента VK.
- Legacy-бот остаётся отдельной low-level реализацией и не участвует в новом
  сценарии.
- Подписки, уведомления, избранные города и мультиязычность в этот этап не
  входят; архитектура должна допускать их добавление.

## Критерии готовности

- Новый бот запускается через `python main.py`.
- Все обязательные сценарии работают в VK.
- Ошибки обрабатываются без traceback для пользователя и без утечки токенов.
- Тесты проходят, документация соответствует реализации.
- Legacy-бот и CLI остаются работоспособными.
